# Architecture & Product Decision Records (ADR)

This document tracks fundamental product, architecture, and growth experience decisions for the Daejeon Random Trip MVP.

---

### ADR-001: Controlled Random Travel vs. Pure Independent Randomness
- **Status**: **Fixed**
- **Decision**: Route generation follows a structured funnel (`Preference -> Zone -> Candidate Filtering -> Route Template -> Place Selection -> Coherent Route`) rather than independently selecting unrelated random spots.
- **Why**: Pure randomness produces nonsensical itineraries (e.g., three consecutive cafes or distant stops across the city). Controlled randomness ensures physical plausibility and structured routing while preserving the excitement of surprise.
- **Revisit when**: If user feedback demands fully open-ended exploration across unlimited categories.

---

### ADR-002: Separation of Recommendation Engine and Visual Slot Animation
- **Status**: **Fixed**
- **Decision**: The recommendation engine (`src/lib/random`) computes the complete `RouteResult` first; an adapter layer maps the variable-stop route to the visual slot reel display format. The slot machine UI is solely an animated presentation layer that stops on the computed result.
- **Why**: Decoupling prevents visual rendering bugs from corrupting itinerary logic, keeps stop counts independent of visual reel counts, and ensures independently testable route logic. READY reels display presentation-only placeholder items without exposing itinerary data early.
- **Revisit when**: Never for the core engine separation; visual interaction styles and adapter mapping may evolve independently.

---

### ADR-003: No Runtime LLM for Route Generation
- **Status**: **Fixed**
- **Decision**: The MVP uses static curated templates, candidate place data, duration budgeting, and controlled random selection/validation logic instead of calling runtime LLM APIs.
- **Why**: Eliminates runtime API costs, latency (crucial for quick slot spin feel), hallucinated locations, and rate-limiting failure modes during marketing campaigns.
- **Revisit when**: Future phases require dynamic natural-language storytelling or personalized multi-city generative guides.

---

### ADR-004: Primary Conversion Metric as a High-Intent Proxy
- **Status**: **Fixed**
- **Decision**: Track clicks on outbound map links within the in-app Route Guide (`place_map_click`) as the Primary High-Intent Proxy Conversion. Today's Pick banner-click tracking is TBD/deferred (ADR-015, revised) — no secondary event is currently defined for it.
- **Why**: Physical visits to Daejeon cannot be directly tracked or verified by a lightweight web landing page without intrusive native app permissions or physical beacons.
- **Revisit when**: Offline verification partnerships (e.g., stamp tours, merchant QR codes) become available.

---

### ADR-005: Strict PII and Free-Text Prohibition in Analytics
- **Status**: **Fixed**
- **Decision**: Do not explicitly collect or send Visitor Log nicknames, message strings, IP addresses, or arbitrary user input to Google Analytics 4 as custom parameters or user properties.
- **Why**: Supports privacy-by-design and reduces the risk of accidental PII/free-text leakage.
- **Revisit when**: Never (permanent privacy rule).

### ADR-006: Separation of Product Policies from UI Hard-coding
- **Status**: **Fixed**
- **Decision**: Business rules (duration budget bounds, preference types, zone weighting, Seongsimdang inclusion rules, avatar lists) must live in `src/config/` and `src/data/`, not inside React components.
- **Why**: Enables rapid policy adjustments during marketing campaigns without risky code refactors or UI regressions.
- **Revisit when**: Never.

### ADR-007: Two-Question Interaction Flow & State Progression
- **Status**: **Fixed**
- **Decision**: Present two sequential setup questions (`Q1`: Duration, `Q2`: Preference) before transitioning through `READY` → `SPIN` → `RESULT` → `ROUTE_GUIDE`. Primary Spin Action is `“여행 뽑기!”`. The slot lever is strictly a visual feedback/interaction mechanism.
- **Why**: Minimizes setup friction while capturing the minimum essential parameters needed for route template selection and duration budgeting.
- **Revisit when**: Analytics show significant drop-off between Q1 and Q2.

### ADR-008: Centered Result Card Action Hierarchy (Superseding Inline Result Sheet)
- **Status**: **Fixed (Supersedes legacy inline long receipt)** — implemented via `ResultArea.tsx` / `SlotOutputLayer.tsx`, Human Browser validated.
- **Decision**: Result presentation adopts the 2-stage reveal flow (output slit peek cue followed 300–500ms after the peek cue is triggered by a front-facing centered `Result Card` modal overlay, rendered as an in-flow `fixed` overlay — not a Portal, since `MainExperience` mounts twice for desktop/mobile and a Portal would escape that responsive gate). The Result Card features three distinct action pathways:
  1. **Conversion (Primary)**: `“이 코스로 가보기”` → Transitions to the in-app `Route Guide`.
  2. **Referral (Secondary)**: `“내 루트 공유하기”` → Generates snapshot and short URL `/r/[shareCode]`.
  3. **Participation / Reward (Tertiary)**: `“랜덤 로그 남기고 1회 더 뽑기”` → Opens in-flow Visitor Log composer and unlocks 1 reroll upon server-verified DB save.
  - Result Card body is semantic React / DOM / CSS; glassmorphism is prohibited; slot machine remains stationary.
  - Result Card keyboard ownership (Escape-to-minimize, Tab focus containment) is active only while Result is the topmost interactive layer; it suspends automatically whenever `RouteGuideModal` or `GuestbookComposer` is open above it, and reactivates — without minimizing Result — once the nested overlay closes.
- **Why**: Eliminates layout jumping and viewport displacement caused by long paper extrusion while focusing user attention on structured conversion, referral, and community participation.
- **Revisit when**: Post-launch campaign analytics show significant conversion drop-offs.

### ADR-009: Target Audience Assumption (20–30s)
- **Status**: **Tentative**
- **Decision**: Treat the 20–30s demographic as a working marketing campaign segment rather than a hard product constraint.
- **Why**: Marketing copy and visual motifs (Y2K retro) are hypothesized to appeal to this segment, but the underlying product value (effortless local travel discovery) may resonate across wider audiences.
- **Revisit when**: Post-campaign audience insights, channel engagement, and conversion evidence reveal actual visitor distribution.

### ADR-010: Initial Geographic Cluster Scope
- **Status**: **Tentative**
- **Decision**: Seed candidate place data primarily around Daejeon Station and the old downtown district (Eunhaeng-dong / Daeheung-dong).
- **Why**: High density of walkable attractions, dining, and transit access simplifies MVP travel viability.
- **Revisit when**: Expanding the tourism database to Yuseong, Dunsan, or Daedeok clusters in subsequent iterations.

### ADR-011: Visitor Log & 1-Time Reroll Reward Loop (Superseding Unconditional Free Rerolls)
- **Status**: **Fixed (Supersedes legacy unconstrained free reroll policy)**
- **Decision**: Deprecate unconditional free rerolls. Rerolls start `locked`. Submitting a Visitor Log (Kkumssi avatar, 2–12 char nickname, max 50 char message) triggers a server-side DB `INSERT` into `guestbook_entries`. Upon verified success, the user receives exactly 1 reward reroll (`available` → `consumed`) backed by browser `sessionStorage`. Maximum 1 reward reroll per travel session.
- **Why**: Converts reroll demand into community social proof and active engagement without introducing user login complexity.
- **Revisit when**: Moderation/spam issues arise or campaign scale requires authenticated accounts.

### ADR-012: Approved Visual v4 Base & Visual Skin Boundaries
- **Status**: **Tentative (Approved Visual Base)**
- **Decision**: Adopt Visual v4 ("Korean Y2K Personal Web × Random Travel Toy" structure: Header `DAEJEON RANDOM TRIP`, Left Sidebar `MY PROFILE` / `TODAY IS…` / `BGM PLAYING`, Center `Setup Area` → `Slot Anchor` → `Result Overlay` → `Route Guide`, Right Sidebar `TODAY’S PICK` / `VISITOR LOG`). Direct legacy terminology is avoided in architectural models. Full-screen image slicing and glassmorphism are prohibited.
- **Why**: Maintains emotional brand identity while keeping presentation concerns cleanly modular and responsive.
- **Revisit when**: Design team delivers future theme skins or asset updates.

### ADR-013: In-App Route Guide Architecture Over Direct Map Redirect
- **Status**: **Fixed**
- **Decision**: Clicking `“이 코스로 가보기”` does not directly navigate away to an external map app. Instead, it opens an in-app `Route Guide` view displaying total estimated travel time, stop sequence (1–4), stay durations, transit times, tips, and individual outbound map links (`place_map_click`).
- **Why**: Direct external redirects discard the coherent itinerary context, whereas an in-app Route Guide gives users the structured plan they need before choosing which individual stop to open in navigation.
- **Revisit when**: Deep linking / multi-stop map route sharing APIs become viable across major Korean map providers.

### ADR-014: Referral Loop via Shared Route Snapshot URL (`/r/[shareCode]`)
- **Status**: **Fixed**
- **Decision**: Clicking `“내 루트 공유하기”` creates an immutable JSON snapshot in `shared_routes` via server API and generates a short URL (`/r/[shareCode]`, e.g., `/r/F7k2Ma9Q`). The `/r/[shareCode]` page is a dedicated friend landing (`noindex`) featuring the route snapshot and two CTAs: Primary `“나도 여행 뽑아보기”` (referral acquisition) and Secondary `“이 코스 그대로 가보기”` (opens Route Guide). Kakao SDK / Login is omitted in favor of Web Share API and clipboard copy.
- **Why**: Query-string route serialization is fragile and messy. Snapshot storage guarantees permanent route immutability even if place data is updated later, and provides a clean viral landing page for new users.
- **Revisit when**: Dynamic Open Graph card generation is a prioritized non-blocking enhancement within the MVP cycle; dedicated Kakao Talk SDK / message templates remain strictly out of scope.

### ADR-015: Today's Pick as a Right Rail Editorial Banner (Revises Prior Detail-Page / Q2-Seeding Scope)

- **Decision**: Today's Pick remains a Right Rail editorial / visual banner surface only. A banner may optionally hyperlink to an external site related to the featured artwork/place/theme. No dedicated `/pick/[slug]` detail page, no Q2 preference-seeding CTA, and no Today's Pick → Slot funnel are approved.

Today's Pick is confirmed as a simple editorial surface rather than a secondary discovery/seeding funnel, avoiding unapproved complexity and an unreviewed second entry point into the Slot experience.

### ADR-016: Elimination of Main Navigation Tabs to Maximize Slot Viewport Priority
- **Status**: **Fixed**
- **Decision**: Remove legacy top navigation tabs (`여행 뽑기`, `가이드`, `맛집 리스트`, `내 보관함`).
- **Why**: Top tabs implied multi-page portal browsing and directory search, contradicting the core value proposition (“계획하지 말고, 대전에서 여행을 뽑아보자.”). Removing them recovers vertical screen real estate and immediately focuses the user on the Setup Area and Slot Anchor.
- **Revisit when**: Post-MVP product scope explicitly introduces multi-city or complex user dashboard capabilities.

### ADR-017: Selective Persistence Boundary (Supabase for Guestbook & Shares Only)
- **Status**: **Fixed**
- **Decision**: Limit Supabase persistent storage strictly to `guestbook_entries` and `shared_routes`. General route generation and Q1/Q2 selections are ephemeral; reroll session states are managed in session-scoped browser storage (`sessionStorage`).
- **Why**: Minimizes database write volume, eliminates latency from the core slot spin interaction, and maintains strict privacy by avoiding storing anonymous browse sessions.
- **Revisit when**: Persistent user accounts or cross-device itinerary sync are added in future versions.

### ADR-018: Route Stop Count and Provisional Duration Policy
- **Status**: **Fixed**
- **Decision**:
  - **Half-Day (`half`)**: Fixed **3 stops** (2-stop half-day templates are deprecated and removed).
  - **Full-Day (`full`)**: **3–4 stops** (4 stops preferred when `stay-extender` candidates are available; 3 stops retained as graceful fallback).
  - **Duration Budgets**: Numeric duration bounds (`minMinutes`, `maxMinutes`) remain unconfigured (TBD) in `DURATION_BUDGET_POLICIES`. In provisional MVP data, `estimatedTotalMinutes` strictly represents place stay time ($\sum \text{Place.durationMin}$) without inter-stop transit time.
- **Why**: 2-stop half-day routes generated insufficiently engaging itineraries with low stay times (min 65m, p10 95m). Fixing half-day to 3 stops naturally lifts the duration floor (min 115m, p10 145m, median 175m) and guarantees 100% route generation success across all 7 active zones without requiring brittle numeric rejection loops on provisional place data.
- **Revisit when**: Place candidate dataset undergoes full tourism verification and door-to-door transit time modeling is implemented.

### ADR-019: Ordered Route Template Sequence & Preference-Preserving Fallback
- **Status**: **Fixed**
- **Decision**:
  - **Half-Day (`half`)**: Fixed sequence of exactly 3 stops: `Meal → Cafe → Preference`.
  - **Full-Day (`full`)**: Primary sequence of 4 stops: `Meal → Cafe → Discovery → Preference`.
  - **Full-Day Graceful Fallback**: If a 4-stop itinerary cannot be fulfilled in a zone, gracefully fall back to 3 stops (`Meal → Cafe → Preference`), omitting intermediate `Discovery` while strictly preserving the user's explicit Q2 Preference selection.
  - **Slot & Role Boundaries**: Canonical cafe identification is based on `PlaceCandidate.category === "카페·디저트"`. The conceptual `CandidateRole` taxonomy (`anchor`, `meal`, `discovery`, `stay-extender`) remains unchanged.
- **Why**: Pure role-based random ordering produced unnatural sequences (e.g. meal placed at the end of a half-day trip). The Ordered Route structure guarantees coherent, intuitive local itineraries (Meal -> Cafe -> Activity) while keeping randomness and zero database overhead.
- **Revisit when**: Multi-city extensions or dynamic duration-window constraints are introduced.

### ADR-020: SlotVisualFrame / LogicalCanvas Separation
- **Status**: **Fixed**
- **Decision**: The slot machine's physical visible footprint (`SlotVisualFrame`) participates in normal page layout flow, sized to the production assets' measured non-transparent pixel bounds (~46.72% of the 600×500 logical canvas width, not the previously assumed ~58%). The original 600×500 asset coordinate system (`LogicalCanvas`, containing reels/PNG/CTA) is absolutely positioned inside the frame and must never determine surrounding layout spacing.
- **Why**: Letting the transparent logical canvas itself participate in layout required hand-tuned negative margins to compensate for its padding, which drifted out of sync at every viewport and could never be fixed by re-tuning constants alone. Separating "physical footprint" from "asset coordinate system" removes the compensation entirely.
- **Revisit when**: The production slot PNG assets (`slot-idle.png` / `slot-pulled.png` / `slot-shell.png`) are re-exported at different bounds — the measured constants in `src/components/experience/slotGeometry.ts` would need re-verification.

### ADR-022: SlotOutputLayer as a Sibling of SlotVisualFrame
- **Status**: **Fixed** — implemented via `SlotOutputLayer.tsx`, mounted from `SlotAnchor.tsx` at the sibling position reserved for it; Human Browser validated.
- **Decision**: The Result/Ticket output reveal (ADR-008's output slit peek cue) mounts inside `SlotStage` as a **sibling** of `SlotVisualFrame` — never as a descendant of `LogicalCanvas` or inside the frame's clipped bounds. ### ADR-023: Result Minimize / Reopen (결과 접기) Resolves the Result Dismissal Path
- **Status**: **Fixed** — implemented via `revealStage: 'minimized'` in `MainExperience.tsx`, `ResultArea.tsx`, and the reopen affordance in `SlotAnchor.tsx`'s helper band; Human Browser validated.
- **Decision**: The Result Card is dismissed by **minimizing** (결과 접기), never by closing or discarding. Minimizing sets the presentation-only `revealStage` to `'minimized'`: the overlay hides (`display:none`, not unmounted, so `ResultSheet`'s local share state survives), body scroll and background interaction are fully restored, and `state.result` is never touched — no route regeneration, no reducer dispatch. A persistent reopen affordance (`🎫 내 여행 티켓 다시 보기`) lives in `SlotAnchor`'s helper band, directly beneath the slot's output slit (zero added layout height, preserving the ADR-020 position-lock contract), and returns to the exact same revealed Result Card with every CTA/reward/reroll state intact. Escape, while Result holds keyboard ownership (ADR-008), also minimizes rather than closing or discarding.
- **Why**: ADR-008 established the centered Result Card modal overlay but left dismissal undefined. A persistent overlay with no exit trapped the user — background scroll-locked and click-blocked with no way out — and was explicitly flagged as an open Product/UX question during implementation. Minimize resolves it while preserving Result data and the ticket metaphor ("결과가 접혀 있다", not "결과가 사라졌다").
- **Revisit when**: Product wants an actual close/discard action distinct from minimize, or the reopen affordance's placement needs revisiting for discoverability.

### ADR-024: Landing Page Columns Stay Out of Their Own Stacking Context
- **Status**: **Fixed** — implemented via `src/app/page.tsx`; Human Browser validated.
- **Decision**: The three-column Visual Stage layout (`src/app/page.tsx`) does not assign `z-index` to the Left Sidebar, Center (`<main>`), or Right Sidebar column wrappers. Only the shared content wrapper they sit inside keeps `z-10`, which is enough to stay above the decorative Ground Scenery (`z-0`).
- **Why**: `z-index` on a flex item creates a stacking context even without an explicit `position`. All three columns previously carried `z-10`, so every in-flow `fixed` overlay inside `MainExperience` (Result Card, Guestbook Composer, the reveal-emphasis backdrop) resolved its own `z-index` inside `<main>`'s local stacking context instead of the page's — DOM order then decided paint order between columns, so the Right Sidebar (rendered after `<main>`) visually painted over these overlays while the Left Sidebar (rendered before) did not. Removing the redundant column-level `z-index` lets in-flow fixed overlays cover the whole page as intended, without a Portal — which would reintroduce the dual-mount hazard of `MainExperience` rendering twice for desktop/mobile (see ADR-008).
- **Revisit when**: A future column needs its own `z-index` for an unrelated reason — re-verify against this contract before adding one.

### ADR-025: Random Log — Public Read IA, Result-Gated Writing, and Reward/Write Decoupling
- **Status**: **Fixed** — implemented (public read surfaces, `CharacterSelector`, write/reward decoupling) on branch `feat/random-log-right-rail`; Human Browser validated. Extends ADR-011, which remains accurate and unmodified.
- **Decision**:
  1. **Public read IA, three tiers, ungated**: Right Rail live preview (top 3, `RandomLogRightRailPreview`) → `/random-log` full board (cursor-paginated "Load more") → `/random-log/[id]` detail. All three are reachable directly from the landing page before any slot spin; none depends on `phase === 'result'` or any session state. The board is not optional scaffolding around the detail page, and the detail page is not a modal.
  2. **Result-gated writing, no landing-page entry point**: Writing a Random Log still requires an active generated Result, exactly as ADR-011 established (`Result` → "랜덤 로그 남기고 1회 더 뽑기" / "랜덤 로그 남기기" → `GuestbookComposer`). The Right Rail's only affordance into the write flow is none at all — it links to the read surface, never opens `GuestbookComposer`.
  3. **Once-per-Result client UX guardrail**: A Result may be logged at most once within the current mounted client session, tracked via `loggedRouteIds` (a plain `Set<string>` in `MainExperience`'s React state, keyed on `RouteResult.id`). Deliberately **not** persisted to `sessionStorage`, not a DB column, and not a uniqueness constraint — `state.result` itself is never persisted across a reload, so there is nothing to guard after one.
  4. **Writing eligibility separated from reroll reward eligibility**: These were previously one CTA switched on `rerollReward` alone (`'locked'` was the *only* branch that opened `GuestbookComposer`), which made the composer permanently unreachable once the reward reached `'consumed'`. `ResultSheet` now renders two independent CTAs — a Random Log CTA driven by `hasLoggedCurrentResult`, and a reroll CTA driven by `rerollReward` alone, hidden entirely (not disabled) outside `'available'`. `GuestbookComposer` receives a `rewardEligible` prop from the same `rerollState` (never a duplicated state machine) and **snapshots** it into local state at submit time — reading the live prop in the success view is wrong, because a reward-granting submission synchronously flips `rerollReward` in the same React batch that shows the success screen, which would make even a real reward-unlock report as non-reward after the fact.
  5. **One rewarded reroll per browser-tab session, unchanged**: `rerollSession.ts` (`unlockRerollReward` / `consumeRerollReward`) was not modified. Its existing guard — refuse to re-unlock once `'consumed'` — is what makes a later Random Log submission safe to allow at all: logging Result B can never grant a second reward, without any new code enforcing it.
  6. **Public identifier reuses the existing UUID, behind a data-access boundary**: `/random-log/[id]` uses `guestbook_entries.id` directly — no migration, no new `public_code` column. Safe because the table has no anon/authenticated RLS policy (server-only, `status='visible'`-filtered access) and a UUIDv4 is not sequential/enumerable. The detail page reaches the row through exactly one function, `getGuestbookEntryByPublicId` (`src/lib/database/guestbook.ts`), never an inline query, so a future move to a `shared_routes.share_code`-style short code changes only that function's internals.
  7. **Production character artwork remains deferred**: `GUESTBOOK_AVATARS` (`src/config/avatars.ts`) now holds the 10 real Kkumssi-family identities from the Figma handoff as stable ids (`mongmong`, `kkumdongi`, `nebeu`, `geumdori`, `kkumnuri`, `kkumdori`, `doreu`, `kkumbichi`, `eunsuni`, `kkumsuni`), replacing the earlier 4 generic placeholders — but every entry's `imageSrc` is left unset pending asset extraction; `badgeEmoji` is the structural fallback. `CharacterSelector` is a Hero preview + fixed 5×2 picker (all 10 visible at once, no carousel/scroll-arrows) built to accept `imageSrc` with no redesign once assets land. The `kkumdori` avatar entry is a distinct role from the static `Character/Main/Kkumdori` brand illustration already in `LeftSidebar.tsx` and must not be aliased to it.
  8. **Rendering freshness required an explicit fix**: `export const dynamic = 'force-dynamic'` is set on `/` and `/random-log`. Verified empirically via `pnpm build`: Next.js 16.3.2 does not infer dynamic rendering from an uncached `fetch()` alone on a route with no dynamic segment, so without this, both routes would statically freeze their Random Log data at build time. `router.refresh()` (called in `GuestbookComposer` immediately after a confirmed-successful POST) is the client-side trigger that makes a new submission visible on the current page without a manual reload — it re-renders Server Component data while explicitly preserving unaffected client state (Result reveal/minimize, composer state) and performing no navigation.
- **MVP Abuse Boundary (explicit, intentional)**: The once-per-Result rule and the one-reroll-per-session rule are both client-side UX guardrails, not security controls. `POST /api/guestbook` remains callable with any client-supplied `route_id`. A fresh browser tab/session can trivially re-earn the reward and re-log. No auth, device identity, reward ledger, DB uniqueness constraint, or API rate limiting was added — this is explicitly out of scope for this MVP, matching the existing no-login philosophy (ADR-011, ADR-017).
- **Explicitly deferred / not implemented**: comments, likes/ranking, profiles, edit/delete, social reactions, sharing on Random Log entries; GA4 events for any Random Log surface; production Figma character artwork extraction; a `public_code`-style identifier migration. None of these are documented as implemented anywhere else in this repo's docs.
- **Why**: Product review found that coupling write eligibility to reward eligibility silently deleted the write path forever once the one reward was spent — a real defect, not a design tradeoff. Separating the two into independent, minimally-scoped mechanisms (a session-local `Set`, an existing untouched reward guard, an explicit prop instead of implicit derivation) fixes the defect without introducing accounts, a ledger, or any new persistence tier.
- **Revisit when**: Product wants Random Log write frequency to scale beyond one-per-Result, wants genuine abuse prevention (rate limiting / auth), or approves production character artwork / a `public_code` identifier migration as new, reviewed scope.

### ADR-026: Reduced-Motion Slot — Shared Lifecycle Clock and Reduced-Intensity Reel Roll
- **Status**: **Fixed** — implemented on branch `hotfix/slot-reduced-motion`; Human Browser E2E validated (desktop Chrome with forced `prefers-reduced-motion: reduce`, 400px/375px viewports, reroll re-entry).
- **Decision**: Two independent fixes, both scoped entirely to `prefers-reduced-motion: reduce`; normal-motion behavior and timing are unchanged.
  1. **Shared lifecycle clock**: `MainExperience.tsx`'s spin effect previously special-cased `prefersReducedMotion` with a single `REDUCED_MOTION_TOTAL_MS: 60` timeout that dispatched `completeSpin` and revealed the Result Card almost immediately after SPINNING began — a production regression found post-deploy (reported on a team member's laptop and iPhone Safari; deterministically reproduced via Chrome DevTools' `prefers-reduced-motion: reduce` emulation). This is now one shared lifecycle for both motion preferences: `getMotionTimings(prefersReducedMotion)` (`motionConfig.ts`) selects between `MOTION_TIMINGS` (normal: reel stops at 1100/1600/2100ms, Result at ~2900ms) and `REDUCED_MOTION_TIMINGS` (reduced: reel stops at 650/1100/1550ms, `completeSpin` at ~1800ms, Result at ~2200ms). `MainExperience.tsx` runs a single `setTimeout` sequence regardless of motion preference — only the timing table differs.
  2. **Reduced-intensity reel roll, not a new metaphor**: the vertical reel roll (`@keyframes reel-roll`, `globals.css`) is CSS-only over an otherwise static DOM (`SlotAnchor.tsx` renders the doubled neutral-symbol track once and never re-renders it during a roll), so the pre-existing blanket `.animate-reel-roll-0/1/2 { animation: none !important }` under `reduce` froze the reels for the entire SPINNING duration — this read as `static → snap → snap → snap` in Human E2E even after fix (1) restored deliberate timing. `.animate-reel-roll-0/1/2` are removed from that suppression and instead given reduced `animation-duration` overrides (0.75s / 0.90s / 0.70s vs. normal 0.38s / 0.44s / 0.35s, ~2x slower) — same DOM, same doubled-symbol track, same seamless `-50%` loop, same direction as normal motion, only slower. `.animate-reel-settle`'s bounce (`translateY` + `scale` + `brightness`) is replaced under `reduce` by a new `reel-settle-fade` keyframe — an opacity-only 0.2s fade. `.animate-lever-pull`, `.animate-ticket-entrance`, `.animate-reveal-fade-in`, and `.animate-output-peek` remain fully suppressed, unchanged.
- **Why**: `prefers-reduced-motion: reduce` means reduced motion, not zero product-lifecycle time and not zero visual feedback. The instant-Result shortcut was a functional regression — reduced-motion users could not perceive the "여행을 뽑는다" (drawing a trip) moment at all. The first fix (deliberate timing, all reel animation still suppressed) still failed Human E2E because SPINNING was visually static for its full duration. A reduced-intensity version of the *existing* reel roll — rather than a new symbol-shuffle/opacity-crossfade metaphor, which was fully designed and then explicitly rejected once Product clarified that the approved full-motion Slot is the single visual source of truth for both motion preferences — preserves the Slot's interaction identity while measurably cutting motion intensity (~2x slower; ~10 vs. ~35 symbols visible per reel before its own stop). Reduced-motion CSS changes are isolated entirely inside the existing `@media (prefers-reduced-motion: reduce)` block in `globals.css`; no other file's CSS, JSX, or DOM changed as part of the reel-intensity fix.
- **Explicitly rejected**: (a) special-casing only the `60`ms constant while leaving two divergent lifecycle branches in place; (b) an in-place symbol-shuffle / opacity-crossfade replacement for the reel track (a new JS-driven low-motion visual, distinct from the approved Slot), designed in detail then abandoned once Product corrected the goal to "preserve the existing Slot animation, reduce intensity" rather than "invent a new reduced-motion interaction."
- **Revisit when**: Human E2E or real user feedback indicates the reduced reel-roll speed is still too intense (raise `animation-duration` back toward normal, or switch to `animation-timing-function: steps(12)` for discrete rather than continuous advancement) or feels too slow relative to the approved full-motion Slot (lower the values further toward normal). Both are single-value CSS changes inside the existing media query, requiring no structural rework.

### ADR-027: Central Visual Asset Registry (`src/config/visualAssets.ts`)
- **Status**: **Fixed** — implemented in the Visual Detail Pass; static validation passed, Human Browser E2E pending.
- **Decision**: All production image paths resolve through a single registry, `src/config/visualAssets.ts`, exposing `VISUAL_ASSETS` (36 entries), the derived `VisualAssetKey` type, the `visualAsset(key)` accessor, and `VISUAL_ASSET_META` (intrinsic width/height, recorded only where a component needs an explicit aspect ratio to avoid layout shift). Keys are transcribed verbatim from the per-asset `handoff` labels published in the Figma Production manifest (`oyEWRpRpaslcF3Iyuw3Jfa`, node `151:2`) — e.g. `setup.duration.halfDay`, `editorial.banner.tashu`. The registry holds the 31 assets newly exported from that manifest plus the 5 pre-existing production assets (`slot-idle`, `slot-pulled`, `kkumdori-main`, both footer landscapes) adopted for single-source-of-truth. `slot-shell.png` exists in `public/assets/` but is referenced by no component and is deliberately not registered.
- **Why**: This establishes a four-layer separation — *Figma semantic frame → exported filename → stable code key → feature/component usage* — so each layer can change without touching the others. Renaming a **feature** never requires renaming an asset; re-exporting artwork changes exactly one registry line, never a component. Three pieces of evidence made this the right shape rather than speculative indirection: (a) the design side already authors these keys, so the registry transcribes an existing contract instead of inventing one; (b) the repository already proved the pattern in miniature — `src/config/avatars.ts` maps stable ids to an optional `imageSrc` behind a single `resolveAvatarAsset()` resolution point; (c) `AGENTS.md` mandates config over UI hard-coding, and this pass would otherwise have scattered 31 new string literals across 7 components on top of the 5 already inline.
- **Type safety**: the registry is declared ``as const satisfies Record<string, `/assets/${string}`>``, so a malformed path is a compile error, and `VisualAssetKey` makes a typo at any call site a compile error. Neither catches a *missing file*, so a registry-path existence check (36/36) is a required validation step alongside lint/typecheck/build.
- **Migration scope**: pre-existing call sites were migrated to the registry only in files this pass already edited for another reason (`page.tsx`, `LeftSidebar.tsx`). `SlotAnchor.tsx`'s chassis `src` deliberately remains a literal so that frozen component's diff stays minimal and reviewable.
- **Explicitly rejected**: (a) per-feature asset constant modules, which re-couple asset identity to feature naming — the exact coupling this pass exists to remove; (b) deriving paths from keys by string transformation, which silently breaks the moment one filename deviates from the convention and defeats the compile-time guarantee.
- **Revisit when**: assets need per-breakpoint variants or `next/image` optimization (the registry becomes the natural place to hold a descriptor object rather than a bare path), or the count grows enough that generating the file from the Figma manifest beats maintaining it by hand.

### ADR-029: PF Stardust Typography + Opaque-Fit Asset Compensation (Secondary Visual Tuning Pass)
- **Status**: **Fixed** — implemented in the secondary visual tuning pass; static validation passed. **Human Browser E2E pending, including a hard gate (below) that can still reverse the global font application.**
- **Context**: After the first production-asset integration, Human Browser review confirmed the assets were installed correctly but that the brand logo, Q1/Q2 icons, BGM note, Slot CTA text, SPINNING status text and Random Log right-rail avatars all read as undersized, and that both decorative clouds crossed the browser-chrome divider. A local pixel typeface (PF Stardust, 3 faces) was introduced in the same pass.
- **Root cause found by measurement, which changed the shape of the fix**: opaque pixel bounds were measured for every flagged export. Most carry large transparent margins, so CSS box size and *visible* artwork size had diverged — `setup.preference.food` is 100% opaque while `setup.preference.walk` is 42.7%, i.e. a **2.3× visible-size spread from an identical 20px box**, and `brand.logo.primary` is only 64.7% opaque vertically, so ~35% of its height budget was empty. A uniform size increase would have preserved the inconsistency. The 10 avatars measured ~98% opaque, confirming that one really was a box-size problem.
- **Decision (typography)**: one family via `next/font/local`; `--font-sans` → Stardust, `--font-mono` → Geist Mono unchanged. Static faces registered at 400 / 700 / 800, with the ExtraBold file registered a second time at 900 so the 104 existing `font-black` sites resolve onto a real face rather than by nearest-match — **zero component edits, no synthetic bolding**. Verified in the build output: four `@font-face` rules, the ExtraBold URL emitted once.
- **Decision (compensation)**: exported PNGs are **never modified**. Per-asset scale lives in `VISUAL_ASSET_OPAQUE_FIT` next to `VISUAL_ASSET_META` and is applied in exactly one component, `FittedAsset`, which also forces `pointer-events-none` because the transparent overflow would otherwise swallow clicks on neighbouring controls. Contract is explicit: the **largest** opaque dimension is fitted to the box, aspect preserved — not both axes. Scope limited to the brand logo, six setup icons and the BGM note.
- **Why not trim the PNGs**: trimming would have been simpler and would have made the logo enlargement literally free, but it desynchronises `public/assets` from the Figma manifest exports and makes every future re-export a manual post-process. Keeping the files byte-identical to Figma and expressing the correction as data was judged the better trade.
- **Why the logo box uses the opaque aspect**: sizing by the canvas aspect spends ~35% of the box height on transparency. Giving the box the opaque aspect (622×264) and sizing by width grows visible width 64–86% for **−5 to +5px** of column height, which is what keeps the enlarged logo from pushing `LeftSidebar`/BGM into the ground-scenery artwork.
- **Explicitly scoped out**: the READY block was **not** retuned (only SPINNING was a confirmed finding; READY inherits the font and had one quoted CTA label corrected as a direct consequence of the emoji removal). Q2 4-across icons are **22px, not 28px** — that row is already width-critical from `sm` up, and reaching 28px would require changing option-card internals or the grid, which exceeds an icon-scale change. `decoration.symbol.clover` and `star` have the same padding characteristic but were not flagged and are untouched.
- **Hard gate carried into E2E**: the global font can alter wrapping and intrinsic heights in source-frozen components. If PF Stardust worsens Result Card wrapping, height, or short-mobile primary-action reachability, that is a **blocker for the global font application** — to be reported, not compensated for by editing Result.
- **Revisit when**: the typeface is finalized (convert delivery to WOFF2, ~1.97 MB → ~1.0 MB, and revisit `preload`); or Human Browser judges 22px insufficient for Q2, which would make option-card/grid changes a separately reviewed scope.

### ADR-036: Slot Peek — Shared Experience Engine, Single Overlay Ownership, and Cavity-Clip Reveal
- **Status**: **Fixed** — implemented on `feat/slot-peek`; Human Browser E2E approved. Flips `OUTPUT_PEEK_ENABLED` (ADR-022) from dormant to live and resolves ADR-022's own "revisit when the Figma output-slit ticket asset lands" note **without** a new asset.
- **Decision, four parts**:
  1. **Shared experience engine (cross-breakpoint continuity)**: A new `ExperienceProvider` (`src/components/experience/ExperienceProvider.tsx`), mounted exactly once in `page.tsx`, now owns the entire experience engine — the `useReducer` state machine, `revealStage`, the spin lifecycle (lever/reel timers), `spinningStoppedReelCount`, `pendingResult`, the reroll/reset lifecycle, and the Peek completion clock (including its run-token) — exposed via `useExperienceEngine()`. `page.tsx` still dual-mounts the responsive `MainExperience` (Hero) presentation (`hidden lg:flex` desktop / `lg:hidden` mobile, unchanged CSS/geometry), but both Hero instances now read the *same* engine instance instead of each owning an independent `useReducer`/timer set. Root cause this fixes: because neither dual-mount tree ever actually unmounts on resize (only `display:none` toggles), the pre-existing per-Hero-owned engine meant whichever tree the user had not interacted with sat idling at `phase:'intro'` since first paint — crossing 1024px swapped which of two independently-live, never-synchronized state machines was painted, silently losing READY/SPINNING/PEEK/RESULT. Centralizing the engine into one instance removes this at the source: crossing the breakpoint, including repeatedly and including mid-SPINNING/mid-PEEK, is now a pure CSS repaint with no state to lose, desync, or strand. This mirrors the codebase's own existing precedent for "must mount twice, must behave as one": `BgmProvider` already owns a single `<audio>` element and playback state for the same two permanently dual-mounted trees, for the identical reason.
  2. **Single overlay ownership**: A new `ExperienceOverlays` (`src/components/experience/ExperienceOverlays.tsx`) is the one and only render site for everything viewport-global or Portal-based — the reveal-emphasis backdrop, `ResultArea`, `GuestbookComposer`, and `RouteGuideModal` — mounted once in `page.tsx`, outside both dual-mount Hero trees (previously each was rendered from inside `MainExperience`, i.e. duplicated). None of the four has any dependency on which breakpoint's column geometry is active, so hoisting them changes nothing visible; it removes a latent hazard the shared-engine change would otherwise have introduced: with `revealStage`/`state` now shared, both Hero instances would satisfy the same `isRouteGuideOpen && state.phase==='result'` condition simultaneously, which — left rendered from inside each Hero — would have mounted **two live `RouteGuideModal` Portals to `document.body` at once** and doubled the reveal-emphasis/backdrop dim-blur opacity. With exactly one render call site, this is structurally impossible, not merely unlikely. `ResultArea`'s own in-flow-`fixed`-not-Portal implementation is unchanged (ADR-008); only its mount count and call site moved.
  3. **Peek visual architecture**: `SlotOutputLayer` (mounted by `SlotAnchor` if and only if `revealStage === 'peek'`) renders two clip/transform-based DOM layers, zero new raster assets: (a) a peek window clipped to `SLOT_PEEK_WINDOW` (measured from direct PNG decoding of the production chassis art: lip `left 23.43% / width 46.73% / top 85.02% / height 4.23%`, cavity `left 30.08% / width 33.17% / top 89.41% / height 5.86%`, union window `left 30.08% / width 33.17% / top 85.02% / height 10.26%`, all expressed as fractions of `SlotVisualFrame`) containing a DOM/CSS paper strip (the Result sheet's own measured paper token `RESULT_BODY_PAPER`, a cobalt rail + dark outline echoing the Result sheet's frame signature, and a recessed top shadow — reusing Result's own material tokens rather than inventing new ones); and (b) a foreground occluder that re-instances the *exact* chassis raster `SlotAnchor` is already rendering (`slot-idle.png`/`slot-pulled.png`, passed down as a `chassisSrc` prop so it is guaranteed to be the same cached, already-decoded bitmap) through the identical `LOGICAL_CANVAS_*` transform, clipped via `clip-path: inset()` to `SLOT_OUTPUT_LIP` — derived programmatically from that same measured rect (`slotGeometry.ts`'s `rectToInsetClipPath`), never independently re-typed. This supersedes the historical `OUTPUT_SLIT` constant (removed): that rect's x-range was actually the pedestal footprint, not the slit, and its `top: 97.2%` extended past the chassis bottom into the helper band — the documented root cause of the original DEV placeholder's "plain white rectangle... collided with the helper copy" rejection. Paint order requires the whole layer to sit *above* `SlotVisualFrame` (`z-20` over `z-10`), not below as ADR-022's original dormant paint-order-occlusion sketch assumed, because the cavity is fully opaque in the source chassis art (verified by direct pixel decode) — occluding from underneath would have rendered the paper completely invisible.
  4. **Visibility contract**: Peek visuals exist **only** while `revealStage === 'peek'` — the instant it becomes `'revealed'`, `SlotOutputLayer` unmounts entirely and contributes zero visible pixels; `ResultArea`'s revealed and minimized visuals are the pre-existing ADR-008/ADR-023 surfaces, completely unchanged, with no new "ticket still in the machine" cue. (An intermediate draft of this work briefly proposed keeping the peek layer mounted through `'revealed'`/`'minimized'` as a persistence cue; this was rejected before implementation as an unapproved alteration of the frozen Result/minimized visuals and does not appear in the shipped code.)
- **Motion + completion contract**: The dormant `peekPhase` sub-beat scaffolding (`PEEK_EDGE_AT_MS`, `PEEK_HOLD_AT_MS`, `OUTPUT_PEEK_PROGRESS_BY_PHASE`) — explicitly labelled placeholder, never implemented — is retired in favor of a single `PEEK_TRAVEL_MS` (260ms) CSS keyframe (`translateY(-100%) -> translateY(0)`, transform-only). The paper strip's **base (non-animated) CSS state is HOLD** — no other base transform is set, so suppressed (`prefers-reduced-motion`, unchanged existing suppression entry in `globals.css`), cancelled, or frame-starved, the element simply rests at its untransformed position, which already equals the correct final state; there is no reachable half-revealed state, and low-FPS/dropped-frame conditions degrade visual smoothness only, never state correctness. `OUTPUT_PEEK_TO_CARD_MS` (400ms, the Fixed product beat per `docs/PRODUCT.md` §5.1 / `docs/ARCHITECTURE.md` §5.1) is unchanged and remains the completion authority via a plain `setTimeout` in `ExperienceProvider` — never `requestAnimationFrame` (stops in background tabs) and never `animationend`/`transitionend` (this codebase has none of those listeners anywhere, confirmed by exhaustive grep, and they would in any case be cancelled and never delivered in a `display:none` subtree). Hardened with a **background/frozen-tab deadline-reconciliation contract**: a wall-clock deadline (`Date.now() + OUTPUT_PEEK_TO_CARD_MS`, deliberately `Date.now()` rather than `performance.now()`, since a navigation-relative monotonic clock can itself pause across a true OS-level device suspend, which would make an overdue Peek misreport as not-overdue right when this check needs to catch it) is captured at Peek start; a single scoped `visibilitychange` listener checks it on foreground and, if already passed, completes immediately through the *same* idempotent completion function the timer calls — guarded twice over, by a monotonic run-token (rejects a superseded run) and a functional `setRevealStage` updater (no-op unless still `'peek'`), so the timer and the reconciliation path can never together produce a double transition. The reconciliation path is a pure optimization removing visible lag on resume; the plain timer remains independently sufficient for correctness on its own.
- **Result asset preparation**: `ResultSkinPreload` (`src/components/experience/result/ResultSkinPreload.tsx`), mounted from `ExperienceOverlays` and active only during `phase === 'ready' || 'spinning'`, emits `<link rel="preload" as="image">` hints for the three Result skin bands (header/body/actions), `media`-gated at the same 1024px breakpoint `globals.css`'s `.skin-canvas` switch already uses, so only the variant that will actually render is fetched and no JS breakpoint detection is introduced. This moves an uncached first-run raster fetch out of the SPIN→Peek→Result reveal frame; decoding (vs. fetching) was deliberately left as a separate, not-yet-needed refinement.
- **Explicitly unchanged**: all approved Slot/Result/Route Guide visual geometry and skins (ADR-020, ADR-022's sibling-mount contract, ADR-033), the `svh`-only mobile hero height budget (ADR-031), `useScrollLock`'s refcount contract, and every domain type/reducer transition in `src/lib/experience`/`src/lib/random` (zero changes — Peek is entirely a presentation-layer concern, per ADR-002's engine/UI separation). No new visual asset was created; the registry (`src/config/visualAssets.ts`) and `public/assets/` are unchanged in count.
- **Why**: The dormant ADR-022 scaffold's assumptions did not survive contact with the real chassis art (the cavity is opaque, so paint-order occlusion was a dead end) or with the actual dual-mount architecture (a naive shared-state fix would have introduced duplicate Portals/backdrops). Fixing the cross-breakpoint defect at its root — one engine instance instead of two — was judged in-scope for this branch rather than deferred, because shipping Peek on top of the known dual-reducer architecture would have made Peek itself unreliable across the exact resize/breakpoint conditions the feature is required to survive.
- **Revisit when**: a dedicated Figma asset is later commissioned for the output-slit ticket (this ADR's zero-asset, DOM/CSS-paper approach would need to be explicitly superseded, not quietly replaced); Human Browser or real-device feedback asks for the Peek travel duration/easing to be retuned (a single `PEEK_TRAVEL_MS` and one CSS keyframe change, no structural rework); or a future surface needs the same "must dual-mount, must behave as one" shape, for which `ExperienceProvider`/`ExperienceOverlays` are the now-established pattern to extend rather than duplicate.

### ADR-039: GTM-First Analytics Architecture, Central Event Dispatcher, Session UTM Attribution, Stale-DLV Reset
- **Status**: **Fixed** — implemented on `feat/analytics-tracking`; verified in real GTM Preview mode against container `GTM-K9G6TQBM` during implementation, then merged to `main`, deployed to Vercel Production, container **published**, and confirmed working via production Tag Assistant/GA4 DebugView (`Google Tag - GA4` fires, `landing_view` fires, `GA4 Event - Product Events` fires correctly for the 16-event taxonomy, stale-DLV fix holds). Supersedes the direct-GA4-only state recorded for `6ae03c4` (ADR gap noted in `docs/PROJECT_STATE.md` **G**) as the current, closed-out production analytics architecture.
- **Decision, five parts**:
  1. **GTM becomes the primary loader when configured; direct GA4 is the fallback, never both at once.** `src/app/layout.tsx` renders `<GoogleTagManager gtmId={NEXT_PUBLIC_GTM_ID}>` when that env var is set; otherwise it renders the pre-existing `<GoogleAnalytics gaId={NEXT_PUBLIC_GA_MEASUREMENT_ID}>` when that one is set; otherwise neither renders. The two are structurally mutually exclusive (one `if/else if`, never both branches), because each independently injects its own `gtag.js` and calls `gtag('config', ...)` — GA4 does not deduplicate across separate config calls, so rendering both would double every `page_view`. Removing `NEXT_PUBLIC_GTM_ID` from an environment instantly reverts that environment to the pre-GTM direct-GA4 loader with no code change — this is the rollback path.
  2. **One central, whitelisting dispatcher; no component touches `window.dataLayer` directly.** `src/lib/analytics/` (`events.ts` for the approved 16-event-name/9-param-key/4-UTM-key lists, `dataLayer.ts` for `pushDataLayerEvent`) is the sole call surface, per `AGENTS.md`'s `src/lib/analytics` module boundary. It sanitizes every value (trims/caps strings at 100 chars, drops non-finite numbers, drops non-primitives), silently drops any key not on the approved list, and never accepts PII/free-text params by construction (nickname, Memory Log message, place names, and `share_code` are never read into any event payload anywhere in the 16 dispatch sites).
  3. **One generic GA4 Event tag reads all 16 events, not 16 per-event tags.** The GTM container holds exactly two tags: `Google Tag - GA4` (the base Google tag, firing on Initialization/All Pages — the sole `page_view` source) and `GA4 Event - Product Events` (Event Name = the built-in `{{Event}}` variable, Event Parameters mapped from 13 Data Layer Variables), gated by one anchored-regex Custom Event trigger (`CE - Product Analytics Events`) matching exactly the 16 approved event names. This scales to a 17th approved event by extending the regex and, if it carries a new param, adding one DLV — never a new tag.
  4. **First-touch session UTM attribution, auto-attached to every event; automatic `user_share` tagging on every shared-route link.** `src/lib/attribution/utmSession.ts` captures `utm_source`/`utm_medium`/`utm_campaign`/`utm_content` (never `utm_term`) into `sessionStorage` on first client landing, before `landing_view` dispatches (`AnalyticsBootstrap`, mounted once in `page.tsx`) — first-touch wins for the session, and a later internal navigation carrying no `utm_*` params can never overwrite it. `pushDataLayerEvent` then auto-attaches whatever is stored to every event it sends, so call sites never pass UTM values themselves. Separately, `getAttributedShareUrl` (`src/lib/share/shareHelper.ts`) appends the fixed tag `utm_source=user_share&utm_medium=referral&utm_campaign=daejeon_random_trip_2026&utm_content=shared_route` to every link generated from the Result Card's share flow, via the native `URL`/`URLSearchParams` API so the `/r/[shareCode]` path itself is never altered; the bare `getShareUrl` is preserved unchanged for canonical/OG use, which must stay UTM-free. This is what lets standard GA4 acquisition reports separate an original campaign visitor from a friend opening a shared route with zero additional instrumentation — `navigator.share` never reveals the recipient's destination app, so no platform-specific source is ever guessed.
  5. **Explicit event-specific Data Layer reset, to prevent stale-DLV leakage.** GTM Preview surfaced a real defect during this pass: `todays_daejeon_view`'s `editorial_position` was still resolving during a later, unrelated `q1_select`, because GTM's Data Layer Variables resolve against a running merged model rather than a per-push snapshot — a key simply absent from a push does not clear whatever an earlier push last set it to. Fixed in `pushDataLayerEvent`: every push now explicitly sets all 9 approved event-specific keys (`duration_type`, `preference_type`, `zone_id`, `route_id`, `stop_count`, `editorial_id`, `editorial_position`, `editorial_url`, `share_method`) to `undefined` first, then overwrites only the keys the current event actually provides. The 4 UTM keys are deliberately exempt from this reset — they are session-scoped attribution, not event-specific state, and are meant to resolve identically across every event in the session. Re-verified fixed in the same GTM Preview session.
- **Duplicate-firing safeguards also established by this pass** (see `docs/ANALYTICS.md` §7.2 for the full list): a dual-mount visibility guard (`offsetParent !== null`) for `todays_daejeon_view`, since `page.tsx` mounts `RightSidebar`/`EditorialSpotlightCard` twice (desktop + mobile) behind CSS visibility; a `sessionStorage` claim-before-dispatch for `landing_view` and a `lastViewedItemIdRef` comparison for `todays_daejeon_view`, both guarding against React StrictMode's dev-only double-invoke of mount effects; a per-run dispatch flag so `result_view` fires exactly once per genuine `'peek' -> 'revealed'` transition and never on reopen-from-minimized; `share` firing only on a resolved `'shared'`/`'copied'` outcome, never on cancel/error; `reroll` and `spin` as separate, mutually exclusive dispatch sites; and `random_log_submit` firing only after a confirmed successful `POST /api/guestbook`.
- **Why**: The product needed real launch-ready measurement (GA4 base tracking alone gave no funnel/attribution visibility) without risking a page_view double-count during rollout, without leaking PII into GA4, and without hand-maintaining 16 near-identical GTM tags. Centralizing sanitization/whitelisting in one dispatcher module (rather than trusting call-site discipline across 16 dispatch sites) and centralizing the GTM tag surface to one generic tag (rather than 16) both trade a small amount of indirection for a single place to audit and extend. The stale-DLV reset was added only after GTM Preview actually demonstrated the leak — it was not a speculative defensive measure.
- **Closed out since this ADR was first recorded**: publishing the GTM container, merging this branch, production deployment, and production-environment verification are all now **done** (see the Status line above and `docs/PROJECT_STATE.md` **D**).
- **Still explicitly deferred, not implemented**: shared-route recipient interaction events (`shared_route_view`, `shared_route_guide_open`, `shared_route_slot_click`) — inbound shared-route traffic is already distinguishable via the `user_share`/`referral`/`shared_route` UTM tag plus the `/r/[shareCode]` path alone; a Campaign & Funnel Analysis Dashboard (Looker Studio or similar).
- **Revisit when**: a 17th event is approved (extend the taxonomy in `src/lib/analytics/events.ts` and the GTM trigger regex together, never one without the other); the generic-tag design proves unsafe because an unrelated future `dataLayer` push needs excluding from the Custom Event trigger's regex; or product decides to build the deferred shared-route recipient event family or the Campaign & Funnel Analysis Dashboard.

- **Context**: ADR-037 replaced the 163-record provisional dataset with the 258-record normalized production dataset, discarding the prior dataset's explicit, per-record `roles` array and collapsing `tags` down to exactly the three literal Q2-preference tokens (`food`/`walk`/`photo`). Two functions in `src/lib/random/roles.ts` had a keyword-inference fallback (`matchesRole`, driven by `ROLE_KEYWORDS`) that only took effect when a candidate's `roles` array was absent — after the refresh, this fallback ran for all 258 records, and because it reused the literal words `food`/`walk`/`photo` as substrings inside its own role keyword lists, it silently let `카페·디저트` (cafe) places satisfy the Meal-slot check and let `산책·야간`/photo-tagged places satisfy the Discovery-slot check. A production data-integrity sweep found this made ~46.5% of generated "Meal" stops actually `카페·디저트` category, and separately found that zone eligibility (`getEligibleZones`) never checked whether a zone had a candidate matching the user's *specific* requested Q2 preference — only that it had *some* meal and cafe candidate — so a zone with zero candidates for a requested preference (`daeheung`, for `walk`: zero active `산책·야간` records and zero candidates of any kind carrying the `walk` tag) could still be selected, and the engine's Strategy-2 fallback would then silently substitute an unrelated candidate into the Preference slot while `RouteResult.preference` kept reporting the originally-requested value as if it had been honored.
- **Decision**:
  1. **Route-slot classification is strict, category-based, and mutually exclusive** (`src/lib/random/roles.ts`): `isMealCandidate` = `category === "식사"`; `isCafeCandidate` = `category === "카페·디저트"` (unchanged — this was already the one strict, keyword-free check, per ADR-019); `isDiscoveryCandidate` = `category === "볼거리·문화·체험"` or `category === "산책·야간"`. The `matchesRole`/`ROLE_KEYWORDS` keyword-inference system is removed entirely — no route-slot check ever again infers role from `tags`. `CandidateRole`/`CANDIDATE_ROLES` remain as a type/exported list for a possible future `PlaceCandidate.roles` field, but nothing currently reads it (0/258 records populate it).
  2. **Q2-preference suitability is a separate, tag-based check, never derived from category**: `matchesPreference(candidate, preference)` is now a plain `candidate.tags.includes(preference)` membership check (`'anything'` still matches unconditionally). A place's category never implies a preference match, and a preference match never implies a route-slot role — the same physical place (e.g. a `카페·디저트` with a scenic hook, tagged `['food','photo']`) can be a legitimate `photo`-preference match while never being eligible for the Meal or Discovery slot.
  3. **Zone/template eligibility now requires a genuinely fillable, distinct-place route for the requested preference, not merely a matching tag somewhere in the zone**: `getEligibleZones` gained a `preference` parameter and now additionally requires that at least one of the duration's ordered templates (the 4-stop primary, or its 3-stop graceful fallback) can be completely filled, without place duplication, for that specific preference. This is answered by a new `isTemplateFulfillable` helper that calls the real `fillTemplateSlots` function itself with a throwaway deterministic random source (feasibility — whether a valid combination exists at all — is provably independent of which random source is used, only *which* valid combination comes back depends on it), so the eligibility check can never drift out of sync with the actual fill logic.
  4. **An explicit preference that cannot be honored is never silently substituted**: `fillTemplateSlots`'s Preference-First Reservation strategy now exhaustively tries every preference-matching candidate as the reservation (proven complete because Meal/Cafe/Discovery pools are mutually exclusive by category, so fixing one reservation candidate has no downstream ordering effect on the others); if no reservation yields a feasible combination, the function returns `null` rather than falling through to an unconstrained pick. The caller (`generateRoute`) either retries the smaller fallback template or throws `RecommendationEngineError` — the unconstrained "pick any leftover candidate" path is now reachable only when the requested preference is `'anything'`, where any leftover candidate is a genuine, non-deceptive fulfillment rather than a hidden substitution.
  5. **`daeheung` + `walk` is a confirmed, permanent, genuine source-data gap, not an engine defect**: `daeheung` has zero active `산책·야간`-category records and zero candidates of any kind satisfying `matchesPreference(c, 'walk')`. It is correctly excluded by `getEligibleZones` from explicit `walk` requests and remains eligible for `food`/`photo`/`anything`. No other zone is genuinely insufficient for `food`/`walk`/`photo`. No dataset change was made or is needed — the existing `tags` data already carries sufficient signal for every other zone×preference combination.
- **Why**: The refreshed dataset's collapse of `tags` to exactly the `PreferenceType` token vocabulary, combined with the keyword-inference fallback reusing those same tokens as role-classification keywords, coupled two concepts (route-slot category identity and Q2-preference suitability) that the product/type model had always intended to keep separate (`RouteSlot` vs. `CandidateRole` were already documented as distinct types). Fixing the coupling at its root — making both checks strict and independent — removes the defect class entirely rather than patching the two symptoms (Meal/Cafe contamination, silent preference substitution) independently. Validated with a deterministic sweep across all 16 zones × 2 durations × 4 preferences × multiple seeds (0% Meal-slot/Discovery-slot category contamination, 0 duplicate place IDs, 0 stop-order violations, `daeheung` never selected for `walk`) plus targeted synthetic fixtures proving the fallback-template path, true-infeasibility throwing, and that the exhaustive reservation search finds a valid combination a naive single-attempt greedy pick could miss.
- **Explicitly not changed**: stop-count/order contract (ADR-018/ADR-019, unchanged); `isDiscoveryCandidate`'s two-category union (not narrowed further — `banseok`/`daedong` have 0 active `볼거리·문화·체험` records and rely on `산책·야간` to supply Discovery; narrowing this was judged a larger, separately-scoped change); the 258-record dataset itself (no rewrite — the existing `tags` data was already sufficient once the matching logic was fixed); any UI/Slot behavior (ADR-002's engine/UI separation holds — this is entirely a `src/lib/random` change).
- **Revisit when**: the place dataset is trimmed or re-refreshed again (re-run the deterministic zone×preference coverage sweep before assuming safety); product wants `isDiscoveryCandidate` narrowed to only `볼거리·문화·체험` (would require first confirming `banseok`/`daedong` have adequate discovery-category coverage, i.e. a data change, not just an engine change); or a `daeheung` walk-category data gap is filled, at which point its exclusion from `walk` requests should be re-verified rather than assumed permanent.

### ADR-041: The `food` Preference Slot Requires the `식사` Category (Route-Slot Eligibility, Not a Redefinition of the `food` Tag)
- **Status**: **Fixed** — implemented on `feat/product-polish`. Refines ADR-040 decision point 2 (it does not reverse it): the two axes stay separate, and this adds a third, narrower concept layered on top of the tag axis for one slot only. ADR-018/ADR-019's stop-count/order contract is unchanged.
- **Context**: Q2's `먹방(food)` option promises an extra *meal*, but the ordered route's **Preference** slot could be filled by a `카페·디저트` place. In the ADR-037 dataset every cafe record also carries the `food` tag (`카페·디저트 | food` = 57 records, `카페·디저트 | food,photo` = 23, against `식사 | food` = 87), and `fillTemplateSlots` built its Preference-slot reservation pool from the bare `matchesPreference` tag check — so roughly 40% of a zone's `food`-eligible pool was cafes. A deterministic 16-zone × 2-duration × 60-seed sweep measured **49.0% (940/1920) of generated `food` routes ending on a `카페·디저트` Preference stop**, i.e. half of all 먹방 routes read `식사 → 카페·디저트 → 카페·디저트` (half-day) — two cafes back to back, the Preference stop duplicating the Cafe stop's role. This was never a slot-classification defect (ADR-040 already made Meal/Cafe/Discovery strictly category-based and those slots were filling correctly); it is specifically about what the *Preference* slot may hold.
- **Decision**:
  1. **A new, third concept: route-slot eligibility for the Preference slot** — `isPreferenceSlotCandidate(candidate, preference)` in `src/lib/random/roles.ts`. It first requires the general `matchesPreference` tag match, then, **for `food` only**, additionally requires `isMealCandidate` (`category === "식사"`). `walk`, `photo`, and `anything` pass straight through unchanged.
  2. **`matchesPreference` is untouched** and remains the general preference/tag axis (`candidate.tags.includes(preference)`, `'anything'` unconditional). `food` is *not* globally redefined: a cafe is still a legitimate `food`-tagged place for any other purpose; it simply may not be the route's Preference *stop*.
  3. **One call site**: `fillTemplateSlots`'s Preference-First Reservation pool (`src/lib/random/engine.ts`) filters with `isPreferenceSlotCandidate` instead of `matchesPreference`. The `'anything'` General Assignment path is untouched. Zone eligibility needs no separate change — `getEligibleZones` already answers feasibility through `isTemplateFulfillable` → `fillTemplateSlots` (ADR-040 point 3), so it inherits the new constraint automatically, and an unfulfillable request still throws `RecommendationEngineError` rather than substituting.
  4. **Reservation-search completeness still holds**: a `food` reservation is now itself Meal-slot-eligible, so it competes with the Meal slot for the `식사` pool. It removes exactly one place from exactly one category pool, so per-reservation feasibility still turns only on whether each remaining slot pool is non-empty, and the exhaustive reservation loop remains a complete search.
- **Why not the alternatives**: *Retagging the dataset* (dropping `food` from cafe records) would break the `food` tag's general meaning and is a data change with a much wider blast radius — a cafe genuinely is a food-preference place. *Globally redefining `food` inside `matchesPreference`* would collapse ADR-040's deliberate separation of the general tag axis from slot roles and would silently change any future non-slot consumer of that function. *Adding a `preference`-scoped route template* would change the route contracts, which are fixed. Constraining the single reservation-pool call site is the smallest change that fixes exactly the reported behavior.
- **Validation**: deterministic 16-zone × 2-duration × 4-preference × 60-seed sweep (7,680 route records) captured before and after the change. All 5,760 `anything`/`walk`/`photo` records are byte-identical to the baseline and their eligible-zone lists are unchanged; all 1,920 `food` records are `식사 → 카페·디저트 → 식사` (half) or `식사 → 카페·디저트 → (볼거리·문화·체험 | 산책·야간) → 식사` (full), with 0 duplicated places and 0 `카페·디저트` Preference stops; `food` zone coverage stays 16/16 for both durations (every zone has ≥3 active `식사` records, so a distinct second meal always exists); the erroring-combination set is unchanged (`daeheung` + `walk` only, per ADR-040 point 5). Synthetic fixtures additionally confirm that a zone with a single `식사` record is excluded from `food` rather than served a cafe, that the full-day 3-stop fallback still honors `food`, and that a `식사` record lacking the `food` tag can still fill the Meal slot but never the `food` Preference stop.
- **Explicitly not changed**: `matchesPreference`; `anything`/`walk`/`photo` behavior; the route templates (`half_ordered_3`, `full_ordered_4`, `full_fallback_3`) and their stop order; the 258-record dataset; analytics taxonomy; any UI value or component.
- **Revisit when**: the dataset's tag vocabulary changes (especially if cafes stop carrying `food`, which would make this constraint redundant but harmless); product wants a separate cafe-oriented Q2 option (that would be a new preference token, not a loosening of this one); or any zone's active `식사` count drops below 2, which would make that zone ineligible for `food` — re-run the coverage sweep before assuming safety.

### ADR-042: Product Polish Pass — Canonical Route-Title Wording, BGM Default Volume, TODAY'S DAEJEON Auto-Advance, and a Memory Log Write Affordance
- **Status**: **Fixed** — implemented on `feat/product-polish`. Four independent polish decisions from one pass; (3) revises ADR-028/ADR-038's manual-only carousel contract and (4) revises the "Result is the only composer entry point" wording in ADR-025 / PRODUCT §6.2 / DATA_MODEL §3.1. **ADR-011/ADR-025's reroll reward mechanic is explicitly unchanged by all four.**
- **Context & Decisions**:
  1. **Route titles said `반일`/`당일` while every chip beside them said `반나절`/`하루종일`.** `src/content/labels.ts` had been the canonical duration map since the label-unification pass, but the generated route *title* was still composed from an inline ternary in `src/lib/random/engine.ts`, so Route Guide's header, the Shared Route `<h1>`, and the composer's ATTACHED ROUTE tag all rendered the older vocabulary directly above a canonical chip. **Decision**: the title is composed through `formatRouteTitle(zoneName, durationType)` in `src/content/labels.ts` (derived from `DURATION_LABELS`, so the two can never drift), and `DURATION_BUDGET_POLICIES.displayLabel` now reads the same `DURATION_COURSE_LABELS` pair rather than restating it. Titles persisted **before** this pass live in `shared_routes.title`, an immutable snapshot (ADR-014) that is never rewritten, so a suffix-anchored `normalizeRouteTitle` repairs them at *display* time only — applied in `normalizeRouteResult`/`normalizeSharedRouteRecord` (Route Guide, both input shapes) and in `SharedRouteView`'s heading. Anchoring to the exact legacy suffix (`/\s반일 코스$/`) means a zone or place name containing those characters anywhere else is never touched. This is copy composition, not recommendation logic: a 16-zone × 2-duration × 4-preference × 60-seed sweep is byte-identical to the pre-change baseline for every stop, category, zone, and eligible-zone list.
  2. **BGM started at the media element's default 1.0**, too loud for an ambient loop. **Decision**: `BGM_DEFAULT_VOLUME = 0.25` (`src/config/audio.ts`), applied to the shared `<audio>` element exactly once on mount in `BgmProvider`, latched behind a ref so no re-render, track reload, or play/pause ever re-asserts it. There is no volume UI and no persisted volume preference in the repo today; the one-time application is precisely what guarantees that if either is ever added, whatever value it writes wins permanently. No control, no persistence, and no change to the existing playback UX was added here.
  3. **TODAY'S DAEJEON auto-advance (~10s), revising the manual-only contract.** ADR-028/ADR-038 deliberately shipped a manual carousel; the cost is that a passive visitor sees exactly one of the five production banners. **Decision**: a single `setTimeout` keyed on the active index advances the carousel every 10s, wrapping last→first. Keying the effect on the index makes "a manual prev/next/swipe resets the timer" structural rather than a second reset path, and guarantees one live timer with no stale closure (functional updater only). It pauses on hover, on focus-within (capture-phase handlers on the existing `<section>`), and while `document.visibilityState === 'hidden'`, and is skipped entirely under `prefers-reduced-motion` or with fewer than two eligible items; each resume starts a fresh full interval. **Analytics boundary**: auto-advance uses the plain state setter, never `goNext()` — `todays_daejeon_next`/`todays_daejeon_prev` are *interaction* events and stay strictly manual, so an unattended page can never manufacture them. `todays_daejeon_view` keeps firing per newly-active banner, unchanged, because an auto-shown banner genuinely was shown. **Correction (ADR-047):** this ADR originally claimed that impression volume was bounded by the pauses above. It was not — the rail is permanently mounted at the bottom of the page, so the timer and its impressions ran while the card sat far outside the viewport. ADR-047 adds the viewport-exposure gate that makes the bound real. No event, parameter, or GTM/Looker change in either pass.
  4. **A Memory Log write affordance, because the composer had no discoverable entry point.** *(Shape superseded by ADR-045: the rail's full-width strip described here became a compact action inside the MEMORY LOG header. The behaviour/state rules below are unchanged and still current.)* Memory Log has always been readable before a route exists (ADR-025), but the composer opened *only* from the Result Card's `다시 뽑기` while the reroll reward was `locked` — a reader browsing the log had no way to learn that writing was possible at all. **Decision**: a lightweight, state-aware write strip (`MemoryLogWriteStrip` + presentational `MemoryLogWriteStripView`) sits between the Memory Log heading and its entries, deliberately lighter than the log cards (1px border on the existing cream surface, one CTA, no deco) so it reads as a utility 안내 strip rather than a competing hero card. Exactly one CTA renders per state: **A** no Result → `코스 뽑기`, which scrolls to whichever `MainExperience` mount is visible (new `HERO_EXPERIENCE_ATTR` + `handleScrollToHero`, the mirror image of ADR-038's `handleExploreMore`) and is disabled while `spinning`, since `START_SPIN` clears `state.result`; **B** Result not yet logged → `기록 남기기`, which opens the existing composer via the existing `isGuestbookOpen` flag, so the current route is attached through the unchanged model (`route_id`, `zone_id`, `duration_type`, `preference_type`, `placeNames`); **C** current Result logged → `다시 뽑기`, which calls the **existing** `handleExecuteReroll`. The `/random-log` board renders the presentational view directly with its own static, always-true copy and a `코스 뽑으러 가기` link — that route is outside `ExperienceProvider` and route state is never persisted, so it must not pretend to know the reader's state; no provider, `sessionStorage`, or state persistence was added to make it stateful.
- **Explicitly not changed by (4)**: the reroll reward machine (`rerollSession.ts`, `locked → available → consumed`, one per browser-tab session) — posting a Memory Log is still what unlocks it, and the strip grants nothing; `ResultActions.tsx` and every Result raster/CTA label/geometry (the Result skin is fixed PNG, so no CTA was added, resized, or rewritten there); the composer itself, `/api/guestbook`, and `guestbook_entries`. Because `handleExecuteReroll` no-ops unless the reward is `available`, state C renders its CTA only while it can actually act and otherwise keeps the success copy with no CTA — the same "consumed → hidden, not disabled" rule Result already follows, a render guard rather than a new gate. **Analytics**: no new events and no new params anywhere in this ADR — `random_log_submit` still fires only from the composer's confirmed-success branch, `reroll` only from `handleExecuteReroll`, and the strip's own render and clicks dispatch nothing, so the published GTM container and any downstream dashboard need no change.
- **Also inspected, deliberately unchanged**: the Shared Route acquisition CTA. `SharedRouteView` already renders a primary-weighted `🎰 나도 대전 여행 뽑아보기 → /` (plus `🎰 대전 여행 직접 뽑아보기` on the not-found branch), both entering the existing generation flow — a second or reworded CTA would have been churn, and the share/UTM contract (ADR-035, ADR-039) is untouched.
- **Revisit when**: the editorial pool grows well past a handful of items, or the 10s dwell proves too fast/slow in real session data (it is a single constant); a real volume control is added (nothing here needs deleting — it need only write `audio.volume`); or product decides the Memory Log strip should be stateful on `/random-log` too, which requires persisting route state across a navigation and is a materially larger decision than this pass.

### ADR-043: Tab-Scoped Trip Session — the Current RouteResult and Its Logged Status Survive a Navigation
- **Status**: **Fixed** — implemented on `feat/product-polish` after a Human Browser E2E finding against ADR-042. Extends the client-session tier that ADR-011/ADR-025 established for the reroll reward; changes no reward rule, no API, and no schema.
- **Context**: `ExperienceState` lives in `ExperienceProvider`'s reducer, and that provider is mounted only on `/`. Memory Log has always been readable pre-route, and ADR-042 then put a write affordance next to it — which made a pre-existing gap visible and product-relevant: a reader who generated route A and walked to `/random-log` came back to `/` with the provider remounted from `INITIAL_EXPERIENCE_STATE`, so the app had forgotten route A entirely. The write strip fell back to its no-route state, offering `코스 뽑기` to someone who already had a course, and `loggedRouteIds` was gone too, so an already-logged route could be offered `기록 남기기` a second time.
- **Decision**:
  1. **A tab-scoped trip session** (`src/lib/experience/tripSession.ts`), `sessionStorage` only — the same tier and the same defensive shape as `rerollSession.ts` and `visitSession.ts` (SSR-safe, try/catch around every storage access, never throws). Never `localStorage`, never a cookie, never the database, and never shared between tabs: one tab is one trip, exactly as before.
  2. **Minimum payload**: a schema `version`, the current `RouteResult`, and `loggedRouteIds` (opaque route ids, capped at the most recent 20). Q1/Q2 are *not* stored separately — the restored phase derives `duration`/`preference` from the `RouteResult` itself, so the two can never disagree. No Memory Log content, nickname, or any other user text is ever written here. Presentation state (revealStage, share state, peek timers) is not persisted.
  3. **Restoration is not generation.** A new `RESTORE_RESULT` reducer action is accepted **only** from the pristine `intro` phase, which makes it idempotent (a StrictMode double-invoke is a no-op) and makes it structurally impossible for a late restore to overwrite a live selection, an in-flight spin, or a newer Result. It runs in a mount effect, after paint, so SSR and the first client render still produce the pristine INTRO markup — no hydration mismatch, exactly like the existing reroll-state sync.
  4. **A restored trip comes back minimized**, not revealed: the reader navigated back to a page, they did not ask for a full-screen Result Card. The existing `내 여행 티켓 다시 보기` affordance reopens it. This required one related correction: the minimize-focus effect now fires only on a genuine `revealed → minimized` transition, since a restore *starts* at `minimized` and would otherwise steal focus (and scroll to the Slot) on arrival.
  5. **Stale/malformed data is discarded, not tolerated.** Every field the UI reads unconditionally is validated on read (id/zone/title/createdAt strings, a finite `estimatedTotalMinutes`, `durationType` and `preference` checked against `SUPPORTED_DURATIONS`/`SUPPORTED_PREFERENCES`, a non-empty `stops` array whose every entry is well-formed). Stops are all-or-nothing — a partially valid itinerary is not a route, and silently dropping a stop would misreport the trip the reader drew. A payload that fails validation, is unparseable, or carries a different schema version is **removed** from storage and the app falls back to the normal initial state.
- **Analytics**: hydrating emits **nothing**. `spin` and `reroll` are dispatched only from their own handlers, and `result_view` only from the `peek → revealed` transition, which restoration never enters (it lands on `minimized`). No event, parameter, or taxonomy change; a restored trip is the same trip, never a second conversion.
- **Explicitly not changed**: the reroll reward contract (`rerollSession.ts`, `locked → available → consumed`, one per tab — it was already session-persisted and is untouched); `/api/guestbook`, `guestbook_entries`, and every Random Log read surface; the analytics taxonomy; Result's own CTAs and the ADR-042 strip's A/B/C rules, which simply now see the correct state after a navigation. No authentication and no server-side session were introduced.
- **Resulting product contract (intended, not incidental)**: a drawn route survives a refresh and a `/` ↔ `/random-log` round trip within the same tab; a restored session is treated as already past INTRO and the entry gate is not shown again; the Result Card returns minimized behind the existing `내 여행 티켓 다시 보기` affordance; BGM does **not** auto-start (playback still begins only from INTRO's CTA or the sidebar control, which also keeps it inside browser autoplay policy); and restoration dispatches no `spin`/`result_view`/`reroll`. Autoplay-on-restore was considered and rejected — a returning reader did not ask for sound, and the gate they would have pressed to get it is precisely the one restoration skips.
- **Revisit when**: the trip needs to survive a *tab close* or move between devices (that is an account/DB decision, deliberately out of scope here); the persisted shape changes (bump `TRIP_SESSION_SCHEMA_VERSION` — old payloads are discarded, never migrated); or a future surface needs more than the current Result restored, at which point what to persist should be re-argued rather than grown by habit.

### ADR-044: Trip-Aware `/random-log` Write CTA (One-Time Composer Handoff) and a Secondary CTA Treatment for the Memory Log Write Affordance
- **Status**: **Fixed** — implemented on `feat/product-polish` from two Human Browser E2E findings. Revises two clauses of ADR-042: the board's write strip is no longer "static, always-true copy" (its revisit-when is answered here, now that ADR-043 makes the trip readable off `/`), and the strip's CTA is no longer a solid coral button. Reward contract, composer, API, schema, and analytics taxonomy are all unchanged.
- **Context**:
  1. Once ADR-043 persisted the trip per tab, the board's fixed `코스 뽑으러 가기` became actively wrong: a reader who had just drawn a course was still told to go and draw one, on the very page where they might want to write about it.
  2. The strip's CTA was `border-2 border-[#ff3b3b] bg-[#ff5555] text-white` — byte-identical in treatment to the journey's own primary CTA (`여행 시작하기`, IntroGate). Two solid coral buttons of equal weight competed for the same attention, and the Memory Log one is not the main journey.
- **Decision**:
  1. **The board reads the persisted trip; it does not gain an engine.** `MemoryLogBoardWriteStrip` (`'use client'`) reads `readTripSession()` and `getRerollSessionState()` — two plain sessionStorage reads — in a mount effect (never during render, so SSR and the first client render agree on the no-trip state and hydration stays clean). `/random-log` is **not** wrapped in `ExperienceProvider` and gains **no** composer, no reducer, and no second submit path. States: **A** no persisted trip → `코스 뽑으러 가기` → `/`; **B** trip not yet logged → `기록 남기기` → the handoff below; **C** trip already logged → success copy, plus `여행 화면으로 가기` → `/` while this session's reroll is still `available`, and no CTA once it is `consumed` (mirroring the rail's consumed→hidden rule).
  2. **A one-time URL handoff opens the EXISTING composer.** State B links to `/?compose=memory-log`; on arrival `ExperienceProvider`'s restore effect calls `consumeComposeHandoff()`, which reads the marker once and strips it via `history.replaceState` (preserving the router's own history state, performing no navigation), then opens the same `isGuestbookOpen` composer against the just-restored route. A URL param rather than another stored flag, because this is one navigation's intent, not session state: nothing to clean up if the reader never arrives, a refresh or Back cannot reopen the composer, and a shared/bookmarked link degrades to a plain visit to `/`. It is additionally ignored when the restored route is already logged, so a hand-edited URL cannot reopen the composer for an entry that exists.
  3. **State C stays a link, deliberately.** Executing a reroll needs the recommendation engine, the reward lifecycle, and the spin presentation, all of which live in the provider on `/`. Reproducing any of that on the board would fork the reward contract (ADR-011/ADR-025) into a second implementation, so the board routes the reader to where the action already exists and words the CTA as the navigation it actually is (`여행 화면으로 가기`), rather than labelling it `다시 뽑기` and doing something else.
  4. **Secondary CTA treatment**, applied once in the shared `MemoryLogWriteStripView` so both surfaces and all three labels (`코스 뽑기`, `기록 남기기`, `다시 뽑기`) move together: cream `#fffef9` fill at rest, a thin 1px `#ff5555` outline, ink `#2b2520` label, and a light coral wash (`#ffeeeb`) only on hover/focus-visible, with the focus ring kept. `여행 시작하기` remains the one strong solid primary. Geometry is untouched — same padding, same text size, still full-width in the stacked narrow rail (the flex parent stretches the box) — and neither the strip nor the log cards were redesigned. The disabled state keeps its existing muted treatment.

### ADR-045: The Rail's Memory Log Affordance Becomes a Compact Header Action (Ticket-Stamp Control), Not a Full-Width Strip
- **Status**: **Fixed** — implemented on `feat/product-polish` from a Human Browser E2E finding. Revises the *shape* of ADR-042's rail affordance and the CTA treatment of ADR-044; every behaviour, state rule, persistence contract and analytics boundary those two established is unchanged.
- **Context**: ADR-042's affordance shipped in the right rail as a full-width two-line strip between the MEMORY LOG heading and its entries. - **Decision**:
  1. **The rail block is removed; the action moves into the existing MEMORY LOG header row.** `MemoryLogHeaderAction` renders exactly one compact control opposite the heading, in the slot that row's `justify-between` already reserved (the editorial card's badge occupies the same position, so this is the rail's own existing pattern, not a new one). The header row grows from a 20px content line to a 28px one; the ~100px block and its 12px margin are gone. No negative margins, no absolute positioning, no z-index change, and no footer/landscape geometry was touched — removing the block is the whole fix, which is why the composition is expected back on its own.
  2. **One shared ticket-stamp control** (`MemoryLogActionButton`), used by the rail header AND the `/random-log` write row so the two can never drift: auto width, 28px tall, warm peach paper (`#fff2e9`), a muted coral 1px edge (`#e8a08c`), ink label, a small decorative glyph (🎲 / ✏️, `aria-hidden`), a light coral wash on hover/focus-visible, the landing's own 1px active press, no shadow. `여행 시작하기` (solid `#ff5555`, white label) stays the single strong primary; this is visibly subordinate by size, weight and colour while still reading as a control.

### ADR-046: Production Logo Asset Refresh — Stale Export Replaced, Sourced From the Handoff Node's Transparent Fill
- **Status**: **Fixed** — implemented on `feat/product-polish` from a Human Browser E2E finding ("a small stray white/blue artifact to the right of the logo"). An asset-only change: no code, config, CSS or layout change accompanies it.
- **Context**: `public/assets/brand-logo-primary.png` was a stale export of an older artwork revision. Pixel analysis found two elements in it that the current Figma artwork does not contain: two isolated alpha islands absent from the current artwork — a blue/white blob at **22×33 px from (623,228)** (mean RGB `#a49ea0`, mean α 58, peak α 188 — the reported artifact) and a larger light-blue motif at **42×47 px from (46,128)** (mean RGB `#b6cbeb`, mean α 125). Both regions are empty in the current handoff, verified three independent ways: the flattened render of `01_BRAND / Brand/Logo/Primary` (`160:21`) shows zero deviation from its ground there, and both of the node's transparent image fills (1619×972 and 405×243) have zero alpha there. Nothing in the DOM was responsible — no CSS background, pseudo-element, overlay, sparkle or adjacent asset; the artifact was baked into the PNG.
- **Decision**:
  1. **Replace the file, change nothing else.** The shipped PNG is the current artwork at the production canvas: 680×408 RGBA, real transparency (176,027 transparent pixels), opaque box **622×264 at (40,62)** — byte-identical to the old asset's opaque box, which is why `VISUAL_ASSET_META` (680×408), `VISUAL_ASSET_OPAQUE_FIT` (`scale: 1.544`), the `aspect-[311/132]` boxes and both responsive clamps all stayed valid untouched. 189,184 B → 163,885 B. One reference (`src/config/visualAssets.ts`), one key (`brand.logo.primary`), two consumers (`page.tsx` desktop + mobile) — all unchanged.
  2. **Sourced from the handoff node's transparent image fill, not its node export.** Exporting `160:21` (or its image layer `147:10`) returns a *fully opaque* PNG: the frame paints a `#fbfbfb` ground behind the transparent artwork, so the rendered export has zero alpha at any scale (verified at 1× and 2×; the 1× export is byte-identical across pulls). Since shipping an opaque logo was not acceptable and compensating for it in CSS was explicitly ruled out, the artwork was taken from that same node's own transparent fill (1619×972) and area-resampled — full canvas to full canvas, premultiplied alpha, no crop, no recolour, no pixel removal — to the production 680×408. The result matches the Figma artwork region-for-region, with only sub-pixel anti-aliasing differences along edges and no compact difference anywhere.
- **Explicitly not changed**: the OG/share card (`public/og-daejeon-random-trip.png`, a separate file from a separate node) — it does not share this asset; the visual asset registry counts; any component, geometry or class.
- **Known upstream issue (recorded in section F of `docs/PROJECT_STATE.md`)**: the handoff node still exports opaque. If design turns off that frame background (or publishes a cleaned alias node, the fix already used for the Result skins), a future refresh becomes a plain drop-in with no resampling step. Nothing in the repo depends on that being fixed.
- **Revisit when**: design ships a genuinely new lockup — re-measure the opaque box first, because `scale: 1.544` and `aspect-[311/132]` are both derived from the current 91.5% × 64.7% opaque geometry and only stay valid while that geometry holds.

### ADR-047: TODAY'S DAEJEON Advances and Counts Impressions Only While It Is Actually On Screen
- **Status**: **Fixed** — implemented on `feat/product-polish` from an independent HIGH review finding. Tightens ADR-042's auto-advance and corrects one factual claim in it. No taxonomy, parameter, layout, or carousel-state change.
- **Context**: ADR-042 gated auto-advance on hover, focus-within, tab visibility and reduced motion, and claimed that impression volume was "bounded by the pauses above". It was not. `RightSidebar` — and therefore `EditorialSpotlightCard` — is mounted twice by `page.tsx` and gated only by CSS, and even the displayed mount sits at the bottom of the page (on mobile, below the entire hero). So a reader who never scrolled to the rail still had a timer cycling banners every 10s and dispatching `todays_daejeon_view` for each one. The existing `offsetParent !== null` check answered "is this the displayed responsive mount", which is a different and much weaker question than "did anyone see it": it is true for a displayed card sitting three screens below the fold. The result was inflated impressions that did not correspond to anything being seen, and a permanently running timer on a page nobody was looking at.
- **Decision**:
  1. **One exposure signal, used by both consumers.** A single `IntersectionObserver` on the card sets `isExposed` when at least **50%** of it is inside the viewport (`EXPOSURE_RATIO`). Half the card is the deliberate middle ground: a sliver at the edge of the fold is not an impression, and requiring the whole card would never fire on a short viewport.
  2. **The scheduler runs only when everything holds**: this mount is the displayed responsive one **and** it is ≥50% exposed **and** the tab is visible **and** it is not hovered/focused **and** reduced motion is off. Each is an effect dependency, so losing any one clears the timer and regaining it starts a **fresh full interval** rather than resuming a partial one. The hidden responsive twin lives in a `display:none` subtree, generates no box, therefore never intersects, and so never schedules a timer at all — the dual-mount duplicate is resolved structurally rather than by a second breakpoint check.
  3. **`todays_daejeon_view` now means "was actually exposed".** The impression effect keeps its `offsetParent` and `lastViewedItemIdRef` StrictMode guards and adds `isExposed` as both a guard and a dependency — so a card that mounts below the fold dispatches its first impression the moment it is scrolled to, rather than at mount (wrong) or never (also wrong). An item cannot become active while offscreen any more, since the only two ways to change it are the paused timer and a manual interaction that requires the card to be visible.
  4. **Fails open.** If `IntersectionObserver` is unavailable the card is treated as exposed, so the carousel degrades to its pre-ADR-047 behaviour instead of silently freezing.
- **Explicitly unchanged**: the ~10s interval; wrap last→first; manual prev/next/swipe and their timer reset; the hover / focus-within / hidden-tab / reduced-motion pauses; the analytics boundary (auto movement still uses the plain state setter and can never emit `todays_daejeon_next`/`todays_daejeon_prev`); the event taxonomy and every parameter; carousel state ownership (still local to each mount — per-mount index continuity across a manual resize past `lg` is explicitly not a goal of this pass); and all card geometry.
- **Correction to ADR-042**: its sentence "its volume is bounded by the pauses above" was wrong at the time of writing and is annotated as such in place. The bound is real only with this ADR's viewport gate.
- **Revisit when**: the rail moves somewhere permanently in view (the exposure gate would then be a no-op and could be simplified away), or product wants a stricter impression definition such as dwell time, at which point the gate becomes a debounce on the same signal rather than a new mechanism.
